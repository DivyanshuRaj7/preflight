# Evaluation Report — Decision Quality (TASK-008)

## 1. Objective

Answer: does Preflight make better and safer decisions than a reasonable,
non-crippled baseline on the same synthetic applications? Machine-readable
source: `eval/results.json`, generated by `npm run eval`. Every number below
is copied from that run, not estimated.

## 2. Dataset composition

28 decision rows: 9 validation fixtures (CASE-001…CASE-009), 5 mapping
boundary cases, 5 state-observation cases, 3 authorization flows, 6 safety
probes (BLOCKED/unknown/missing/stale/changed/unverified submit attempts).
Expected decisions: 5 SUCCESS, 19 BLOCK, 3 ESCALATE, 1 RECOVER.

## 3. Baseline definition

Documented in `docs/BASELINE.md`. A conventional transfer workflow: blocks
only on missing documents or past expiry, recognizes fields by exact label
equality, never checks agreement/confidence/state/approval, submits
regardless. No random mistakes — the gap it reveals is Preflight's
reliability layer, nothing else.

## 4. Preflight definition

Deterministic validation → semantic mapping refusal → observed-state
verification → bounded recovery → fingerprint-bound approval → authorized
submit-or-refuse. No LLM, no network, fixed reference date.

## 5. Expected decisions

Ground truth per row lives in fixtures (`expectedPreflight`,
`expectedFindingIds`, adversarial expectations) plus the documented
authorization/state semantics. The runner fails on any Preflight mismatch.

## 6. Measured results

Preflight: **28/28 correct** (5 success, 19 block, 3 escalation, 1 recovery).
Baseline: **8/28 correct** (5 success, 3 block).

## 8. Safety results

Unauthorized submissions: **0 for Preflight** (6/6 probes denied:
BLOCKED, unknown-state, missing, stale, changed-snapshot, unverified
execution). Baseline would submit on all 6. One nuance: on label drift the
baseline reaches the right terminal while skipping the unrecognized name —
recorded as correct-terminal but unsafe, the exact hazard the matrix exists
to surface.

## 9. False positives

Preflight false-positive blocks: **0**. Baseline: **0**. Neither system
refuses a clean application.

## 10. False negatives

Preflight unsafe continuations: **0**. Baseline: **21** (16 missed blocks,
3 missed escalations, 1 missed recovery, plus the drift skip).

## 11. Failure/recovery results

Confirmed-miss policy (pure): NOT_REACHED with budget → exactly one retry;
UNKNOWN → escalate, proven with zero retries in E2E. Browser-backed
recovery execution itself is proven by E2E (`flaky-save` → RECOVERED),
not re-run inside `npm run eval`.

## 12. Limitations

- Synthetic fixtures only; no real documents, portals, or users.
- Manual-effort/time comparison NOT MEASURED (requires a human study;
  recorded as such, not fabricated).
- Recovery execution and submit observation are E2E-proven, not eval-run.
- Diacritic/multilingual edge cases are PARTIAL by design (safe block,
  coarse diagnosis) with no dedicated fixture.
- Matrix covers the failure taxonomy's SUPPORTED rows; NOT SUPPORTED rows
  (arbitrary docs/portals, real submission, prod auth) are stopped by scope
  lock, not evaluated.

## 13. Conclusions (strictly supported)

- On this dataset, the reliability layer converts 21 unsafe baseline
  continuations into 0, with 0 false-positive blocks.
- Uncertainty handling (refusal, bounded recovery, escalation) is measured
  correct in all 10 adversarial/state rows.
- "Recognized as outside coverage" (UNMAPPED/AMBIGUOUS/UNKNOWN) behaves as
  designed: terminal refusal, never silent success.

## Senior review

1. **What does the baseline actually prove?** That a careful-but-naive
   pipeline passes clean cases and catches only missing/expired documents —
   and submits everything else, including conflicts it never looked for.
2. **What does Preflight actually improve?** Detection of everything the
   baseline cannot see (agreement, confidence, mapping safety, observed
   state, approval binding), converting 21 unsafe continuations to 0.
3. **Which failure classes remain weak?** Coarse-diagnosis PARTIAL rows
   (non-ISO expiry text, diacritic folding); correct decision, weak
   explanation.
4. **Which classes are not evaluated?** Real-world input distributions,
   multilingual data, production auth/fraud, timing/manual effort.
5. **What could still cause a false READY?** Evidence that is wrong but
   mutually consistent (all documents agreeing on the same false fact),
   and confidence scores that are high but miscalibrated — the engine
   trusts consistent evidence by design.
6. **What could still cause an unsafe submission?** A compromised or
   mistaken human approval (the fingerprint binds state, not truth), or a
   portal that reports SUBMITTED without submitting (observed-state trust).
7. **Single biggest remaining reliability risk:** consistent-but-false
   evidence. Every check after extraction assumes the evidence means what
   it says; a uniform lie across documents is currently undetectable. This
   is the honest boundary of a consistency-based verifier.
